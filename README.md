# Smart Museum Management System (SMMS)

**Course:** SWE401 Software Engineering, Abu Dhabi University, Fall 2026-2027 (Instructor: Dr. Muhammad Nasir Bhutta)
**Team (Group 5):** Salma Aldhaheri (1078258), Mariam Alnasri (1099216), Wadima Hamad Alshamsi (1086460)

## Problem
Museums usually run collection records, ticketing and visitor information in separate tools. Staff re-enter data, queues form at the entrance,
visitors get no personalised guidance and interactive (AR) exhibits are rare. SMMS integrates collection/inventory management, online ticketing,
AI-based recommendations and chatbot, AR content and analytics in one system.

## Key features
* **Collection & inventory:** artifact records with change history, QR/RFID scan-to-update, search, condition and inspection alerts, exhibitions.
* **Ticketing:** time-slot booking with a 10-minute seat hold, no overbooking under concurrent load, sandbox payment, digital QR tickets, cancel/reschedule, entry validation, live visitor count.
* **Personalisation:** content-based recommendations with reasons (consent-aware), ratings, popular fallback; chatbot answering only from published museum knowledge with a fallback.
* **AR service:** AR content management (20 MB limit), launch data, fallback viewer data, anonymised session records.
* **Analytics:** sales, peak hours, engagement and inventory dashboards with filters and PDF/CSV export (aggregated data only).
* **Security & administration:** e-mail verification, one-time code for staff/manager/admin, role-based access, lockout, audit log, health monitoring, privacy controls.

## Technologies
Python 3.10+ (tested on 3.12; 3.9 and older are not supported), Flask, SQLite (standard SQL; PostgreSQL is the Phase 4 target), PyJWT, cryptography (AES-256-GCM), scikit-learn (TF-IDF, cosine similarity),
ReportLab (PDF), qrcode (QR images), **React 19** web client (source in `client/`, built with esbuild into `smms/static/dist/app.js`), CSS, `unittest` for tests.

## Prerequisites
Python 3.10 or newer, `pip`, and a modern browser (Chrome, Edge, Firefox or Safari). No database server is needed. **Node.js is only needed if you change the React client** - the built bundle `smms/static/dist/app.js` is committed, so `python run.py` works without it.

## Installation and how to run

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m smms.seed                                    # creates smms.db with demo data (also safe on an existing smms.db: adds the 3D models) and prints TOTP secrets
python run.py                                          # http://127.0.0.1:5000
```

Demo accounts (password `Passw0rd1`): `visitor@smms.example`, `staff@smms.example`, `manager@smms.example`, `admin@smms.example`.
Staff, manager and admin need a one-time code: add the TOTP secret printed by the seed script to an authenticator app
(or compute it: `python -c "from smms.security import totp; print(totp('SECRET'))"`).
Payment is a sandbox: the web client pays with token `tok_success`; the token `tok_declined` simulates a declined card.

## Live chatbot and 3D/AR viewer
* **Real-time chatbot:** copy `.env.example` to `.env` and set `GROQ_API_KEY=...` (free, console.groq.com) or `ANTHROPIC_API_KEY=...` (restart `python run.py`). Answers then stream word by word from a language model
  that may only use the published knowledge entries and exhibit records (`POST /api/chat/stream`, server-sent events; it also remembers the last turns of the conversation and
  answers in English or Arabic). Without a key, or if the service is down, the chatbot falls back to the knowledge-base answer and the chat shows a "Basic mode" note.
* **3D / AR:** *Exhibit / AR* now shows an interactive 3D model (`<model-viewer>`, bundled in `smms/static/vendor/`, works offline). "View in AR" opens camera AR on a phone/tablet
  (needs ARCore/ARKit and the site served over **HTTPS**, e.g. `ngrok http 5000`); on a desktop it keeps the 3D viewer. Demo models for all 8 exhibits are generated by `python tools/gen_models.py`;
  real models can be added in the staff "AR content" tab (`.glb`, max 20 MB).

## Configuration
Environment variables (see `.env.example`; defaults work for a demo): `SMMS_SECRET_KEY` (signing/encryption key - set a long random value outside development),
`SMMS_DATABASE` (path of the SQLite file, default `smms.db`), `ANTHROPIC_API_KEY` / `SMMS_LLM_MODEL` (live chatbot, optional), `SMMS_DEV=1` (returns verification/reset links in API responses; set `0` in production), `SMMS_TZ_OFFSET` (museum time zone as hours from UTC, default `4` = UAE; slot times, "today" and the 24 h cancellation deadline use museum time, stored timestamps and session tokens use UTC).
Business rules (session lengths, lockout, hold time, 20 MB AR limit, chatbot threshold) are in `smms/config.py`.

## Differences from the Phase 4 design (please read)

* **Database:** the code uses SQLite (zero set-up) with standard SQL; `schema.sql` is portable but has not been run on PostgreSQL.
  `BEGIN IMMEDIATE` replaces `SELECT ... FOR UPDATE` for capacity control.
* **Web client:** React single-page app (matches the Phase 4 design) built with esbuild instead of Create React App/Vite. Visitor, staff, manager and admin flows (register/verify, book/pay/reschedule/cancel,
  recommendations, chat, scan/update/validate, artifact/exhibition/AR/knowledge-base management, dashboard with filters and PDF/CSV export, account and audit administration)
  were exercised in headless Chromium during review. The mock-ups of Phase 4 (hold countdown, map, 3D viewer, camera scanning) are only approximated: there is no camera QR decoding
  (the scanner field takes the QR text, which a USB scanner types) and no gallery map or 3D viewer.
* **AR client:** the Unity app is not included. The AR service API (launch data, fallback, anonymised sessions, content management) is implemented and tested.
* **Chatbot / language model:** answers are extractive from the retrieved published knowledge entries; the language-model adapter is a stub (`integration.generate_answer`).
  Retrieval uses TF-IDF with light stemming and a small museum synonym list.
* **RFID:** simulated - an RFID tag ID is accepted wherever a QR value is (`/api/scan/<tag>`).
* **Password hashing** is scrypt (standard library) rather than bcrypt/Argon2; personal data (mobile number) is AES-256-GCM encrypted.
* **E-mail / SMS / payment** are sandbox adapters. In development mode (`SMMS_DEV=1`) verification and reset tokens are returned in the API response.
* QR images need the `qrcode` package (`/api/artifacts/<id>/qr.png`, `/api/tickets/<id>/qr.png`).

## API overview

All endpoints return JSON; protected endpoints need `Authorization: Bearer <token>` from `/api/auth/login`.
`POST /api/auth/register|verify|login|logout|password-reset` - `GET/PATCH/DELETE /api/me` - `/api/admin/accounts` -
`/api/artifacts`, `/api/scan/<tag>`, `/api/alerts`, `/api/exhibitions[...]` - `/api/exhibitions/<id>/availability` - `/api/bookings[...]` -
`/api/entry/validate` - `/api/recommendations`, `/api/feedback`, `/api/exhibits/<id>`, `/api/chat`, `/api/kb/...` - `/api/ar/...`, `/api/ar-content` -
`/api/analytics/summary|inventory`, `/api/reports/export` - `/api/audit`, `/api/health`.

## Review notes (changes made while checking the project against the Phase 4 document)
* Session expiry used `datetime.timestamp()` on a UTC value, so sessions were 4 h too long on a UAE server (and wrong on any non-UTC machine); fixed with `calendar.timegm`.
* Slot times were compared with UTC "now"; entry validation, the 24 h cancellation deadline and the live counter now use museum time (`SMMS_TZ_OFFSET`).
* Deactivating an account or changing its role now takes effect immediately (the token no longer carries the authority; the database does).
* Changing the role of a staff member who had created artifacts failed with a foreign-key error (HTTP 500); old role rows are now kept.
* PDF/CSV report follows Table 36 / Fig. 4.12 (filters, generated by, average booking value, peak hour, change vs previous period, bar chart, share %, top exhibits, page number).
* Audit log older than 12 months is purged (FR-43). `GET /api/ar-content` and the `/verify` and `/reset` e-mail link pages were added; the web client gained the missing staff, visitor and admin screens.
* Web client: header showed the text "null" when logged out (fixed); the ◐ button is high contrast, and a new 🌙/☀ button switches night mode (remembered in the browser, follows the system setting at first visit).
* Tests use a fixed clock; seven regression tests were added.
